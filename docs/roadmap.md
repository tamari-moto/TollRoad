## 基本方針

### ヘッドレス優先（M1〜M4 はテキストのまま完成させる）

UI より先に、テキストで60日通しで遊べる状態を作る。理由:

- **バランスに実リスクがある。** 30,000 → 500,000（16倍）は未検証の数字。移動費250/回を払いながら達成可能かは、多数回シミュレーションでしか分からず、それはヘッドレスでしかできない
- **相場メモが戦略の核。** それが面白いかはロジックの問題で、テキストで検証できる
- Godot の UI 反復はロジック反復より遅い。バランス確定を前倒しすれば、UI 完成後の作り直しを避けられる

**条件**: ヘッドレス駆動部を薄く保つこと。M1〜M4 のロジックは100%残り、捨てるのは print 部分だけで、それは回帰ハーネスに転用できる。

### テストフレームワークは導入しない

GUT / GdUnit4 は、この規模に対して依存・バージョン整合・addons 管理の負担が見合わない。代わりに**シード固定のシナリオスクリプト**で検証する。

これは実測に基づく判断である。`--script` モードでは autoload が初期化されないが、素のクラスは直接駆動できる:

```
direct instantiation gold=1000     ← load() + .new() は動く
after add_gold gold=1500           ← メソッド呼び出しも正常
autoload lookup: <Object#null>     ← autoload は取得できない
```

つまり **autoload 経由でしか触れないロジックはハーネスから検証できない**。ロジックは autoload 無しで駆動できる形にしておくこと（クラス設計の指示ではなく、検証可能性の制約）。

ここで最も価値がある検証は「60日通しの不変条件」— シルバーが負にならない、積載超過しない、純資産が再計算と一致する。これはシナリオ型であってユニット型ではない。

プロトタイプの規模を超えたらフレームワーク導入を再検討する。

### M0 — 土台リセット

**到達点**: ヘッドレス実行が `Gold: 30000` を出力し、60日という上限が入り、RNG がシード固定で再現可能になる。

**作業範囲**
- `gold = 1000` → `30000`（仕様との乖離を解消）
- 全日数60の概念を入れる
- **RNG のシード固定の規約を確立する**
- `data/` の記述形式を決める（Resource か JSON か — ここは実質的な分岐点）

**前提**: Q1（実質バグ修正）

**検証**: `--headless --path . --quit-after 30` で出力される gold を確認

---

### M1 — 交易ループ（ヘッドレス） ★キーストーン

**到達点**: **スクリプトで一周できる。** マートロックで鉱石を買い、隣町へ移動し、利益を出して売る一連が、日ごとのログとして出力される。全6都市の価格が毎日再抽選される。

仕様の約6割のルールがここに含まれる。データモデルを網羅的に先に作るのではなく、最小の「遊べるループ」を先に通す。

**作業範囲**: 品目9種、都市6つと環状の隣接、価格式（補正・ゆらぎ）、積載と重量、売買と5%税、移動の日数・費用、日送り

**前提**
- **Q5（ゆらぎの独立性）** — 都市×品目で独立抽選か、品目単位の変動が全都市に乗るか。価格表の性質そのものが変わる
- **Q2（税の対象）** — 総額か利益か

**検証**: シード固定のシナリオで、最終シルバーが手計算値と一致することを assert。不変条件（シルバー ≥ 0、積載 ≤ 40）も確認

### M2 — リスクと製作

**到達点**: カーレオン便が遊べる。黒ゾーンに賭けて襲撃で積荷を全喪失する体験と、ボーナス都市での製作・材料還元が動く。

**作業範囲**: 黒ゾーン経路、22%の襲撃判定、積荷全損（シルバーと島倉庫は無傷）、製作レシピ・手数料90・30%還元の端数処理

**前提**: **Q6（襲撃の判定単位）** — 移動1回あたりか、区間ごとか

**検証**: 襲撃あり/なしの両分岐をシードで固定して確認。積荷が空になりシルバーが変わらないことを assert。1000回試行で襲撃率が約22%になることも確認

### M3 — 成長要素

**到達点**: パッシブ収入が成立する。交易している間も労働者が倉庫に資源を運び、「投資するか交易を続けるか」の判断が生まれる。

**作業範囲**: 島レベル0〜3、労働者の生産、島倉庫、引き取りアクション、騎乗の購入と積載変更

**検証**: N日休息するシナリオで、倉庫が `2 × 労働者数 × N` 増えることを assert

**作業範囲**: 純資産の算出、ランク判定、ゲーム終了処理、相場メモの記録と7日鮮度（データとして）

**前提**: **Q7（破産時の扱い）**、**Q8（60日目の積荷）**

## 依存関係

**順序が固定されるもの**
- 価格 → 交易 → 移動（価格差が無ければ移動が無意味）
- 経済 → 島・騎乗（投資する収入源が先に要る）
- すべて → 純資産・ランク判定

**並行できるもの**
- 製作は品目と価格さえあれば移動と独立
- 航海日誌は受動的な観測者なのでいつでも追加可
- 島と騎乗は相互に独立
- M6 / M7 の画面ごと
- アセット類（`assets/` は空で、何も依存していない）

## 落とし穴

- **決定性の後付けは苦しい。** RNG のシード固定は M0 でやる。RNG 呼び出しが散らばってからでは、バグの再現もバランスのバッチ検証もできなくなる
- **相場メモは UI 機能に見えて中核はロジック。** 表画面は M7 だが、既知価格の記録は M1 から始めないと、表示すべき履歴が存在しない
- **端数処理の規約を M1 で固定する。** 「30%還元・四捨五入」と `基準価格 × 補正 × ゆらぎ` の int 化位置は観測可能で、手計算の期待値がずれる原因になる
- **本当のリスクはコードではなくバランス。** 移動費250/回を払いながらの16倍は未検証。M4 はそれを測るために存在する。ソロ開発で最も過小評価されやすい部分
- **`.uid` の追加漏れ。** 新規スクリプトごとにコミットが必要（[CLAUDE.md](../CLAUDE.md) のルール）。ファイルを一気に増やす場面で漏れやすい
- **セーブ/ロードは仕様書に無かった。** [game_state.gd](../scripts/autoload/game_state.gd) の docstring だけが約束している状態だったが、**やると決めて実装済み**（2026-08-09）。`user://savegame.json` に JSON で保存し、日送りのたびに自動保存、開始画面から「続きから」で再開する。設計と落とし穴は [CLAUDE.md](../CLAUDE.md) の「セーブ/ロード」節を参照
